# 0026. Every block's source span has a start and an end line and column

**Status:** Accepted (2026-11-09). Amends [ADR 0007](0007-source-maps.md) (the source map's field list gains columns and ends). The base of the block actions and `edit_block` differentiators named in [ADR 0025](0025-mizzen-and-lateen.md).

## Context

ADR 0007's source map points at a line; ADR 0022's `SourcePos` carries `file`, `line`, `column`, and `endLine`, but no end column. A line is enough for "edit here" and not for "replace exactly one block": a paragraph, a list item, or a table row sits inside other text on the same line, and a prompt or tool that replaces a whole line can eat its neighbours. Mizzen's differentiators 1 and 3 — "Edit with your agent" on every block, and an MCP `edit_block` that proves nothing outside the block changed — both need the block's exact span. The engine contracts are frozen (ADR 0023, rule 5), so adding the field and widening the map needs this ADR first.

## Decision

1. **Every block carries a full span: start line and column, end line and column.** A block is one element of a rendered page body (a heading, paragraph, list, list item, table, code block, block quote, and so on). `SourcePos` gains `endColumn` and becomes a span: `file`, `line`, `column`, `endLine`, `endColumn`. The end is **inclusive**: it names the block's last character, so `endLine` keeps its current meaning ("the line the node ends on", equal to `line` for a one-line node) and replacing a block means deleting columns `column` through `endColumn` on those lines. Lines and columns are 1-based; columns count Unicode code points and a tab is one column. The invariant is `endLine > line`, or `endLine == line` and `endColumn ≥ column`.

2. **`data-src` encodes a span as `path:line:column-endLine:endColumn`.** The path is relative to the repository root with `/` separators, like `SourcePos.file`. The Markdown stage puts this on every block element; `<sl-component>` already carries it in the shorter forms. The two existing forms keep their meaning: `path:line` and `path:line:column` are a **point** (end equals start), not an implied span, and a reader must not guess an end from a point. Block actions that replace a block require the full five-part form and stay quiet on a point. Parsing takes the last `:` groups before the numbers, so a path containing a colon still parses.

3. **`sourcemap.json` stores the span on what it already records.** Version 0 keeps `version` and `pages`; the `line` field stays required, and `sections` and `links` gain optional `column`, `endLine`, and `endColumn` with the same units. A missing end means the level-0 or level-1 map of ADR 0007, so existing producers stay valid and a reader falls back to line-only. The map does not grow a per-block list: the block map is the HTML itself, where every block carries its span on `data-src`; duplicating every block in a second file would double the output for data the page already has.

4. **A block's ID is the start of its span: `file:line:column`.** One source file builds one page, and two blocks cannot start at the same position, so the ID names exactly one block of one page — for example `docs/guide/install.md:12:1`. It is derived only from the source bytes: not from build order, element counters, output hashes, or the theme, so **identical builds produce identical spans and identical IDs**. "Identical" means the same engine version, sources, and config; a change that moves a block's start is a contract change and needs its own ADR. The ID is stable across builds, not across source edits: any edit shifts the spans below it, which is why `edit_block` also takes the source hash the agent read and refuses a stale one. A heading's `id` attribute stays the anchor ID and is not the block ID, so headings and every other block kind behave alike.

5. **The implementation (`engine.source-spans`) may change exactly two frozen files:** `packages/engine/src/contracts/source.ts` (add `endColumn`) and `schema/sourcemap.schema.json` (the optional span fields of decision 3). No other frozen contract changes, and the engine still knows nothing about the theme. Everything else this decision needs — emitting `data-src` on every block, the SARIF region's end column, `spec/sourcemap/v0.md` and `docs/source-maps.md` moving in lockstep with the schema, and `packages/doctor` reading spans — is implementation owned by its own roadmap tasks, which this ADR constrains but does not amend.

## Consequences

- Prompts and tools can name one block exactly: "replace `docs/guide/install.md:12:1-12:24`" replaces a paragraph and nothing else, on a line that may hold other text before and after it.
- `SourcePos` widens for every consumer: `Page.source`, `Heading.pos`, diagnostics, and the theme's tests that write `SourcePos` literals gain one field. TypeScript flags literals that omit `endColumn`, so the change is found at compile time.
- `packages/doctor`'s `ae.edit-prompt.source` check and the `data-source` name in the content contract's comment read the point form today; a follow-up aligns their name and teaches them spans.
- Point-form `data-src` remains valid forever, so a producer that knows a line but not a column still renders a usable map.
- **Not verified:** the stability claim against a real `fixtures/docs-site` build (the implementation issue tests it), span behaviour for blocks inside list items and block quotes whose Markdown syntax occupies columns of the same line, and how surrogates in CJK text count against the code-point rule.
